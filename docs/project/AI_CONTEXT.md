# AI_CONTEXT — как работать над этим проектом

> Операционные правила для ИИ-ассистента. Факты о проекте — в [PROJECT_STATE.md](PROJECT_STATE.md), нарратив — в
> [HANDOVER.md](HANDOVER.md). Здесь — КАК работать, а не ЧТО сделано. Прочитай это до написания любого кода.

## Что это (в двух абзацах)
Club — utility-клиент Minecraft (Fabric 1.21.1, Java 21, `com.club`). Идёт многоэтапная миграция UI на новый
рендер-стек `com.club.ui` (MSDF-текст + аналитический SDF-фигуры), чтобы получить качество уровня премиальных
оверлеев. **Stage 1 (рендер-фундамент) завершён и в `main`.** Дальше — Stage 2 (токены + компоненты), 3 (ClickGUI),
4 (HUD), 5 (перенос функционала, ретайр legacy). Полный roadmap — [ROADMAP.md](ROADMAP.md).

Фундамент — это контракты (`UiRenderer`/`UiText`/`UiContext`/`Ui`) и два бэкенда (`Modern*` GPU, `Legacy*` fallback).
Компоненты будущих этапов рисуют ТОЛЬКО через `Ui.renderer()`/`Ui.text()`. Архитектура важнее скорости.

## Категорически нельзя
- **Нарушать backend-only.** Вне `com.club.ui.backend.*` запрещены `RenderSystem`/`BufferBuilder`/`Tessellator`/
  `BufferRenderer`/`GlUniform`/`ShaderProgram`/`DrawContext.fill`/`.drawText(`/`ClubFont`/`RenderHelper`. Рендер — только
  через `Ui.renderer()`/`Ui.text()`. Это проверяет `ArchitectureRuleTest` — он должен оставаться зелёным.
- **Трогать существующие `gui/*`, `hud/*`, `Theme`, `ClubFont`, `RenderHelper`** — до Stage 5. Новый стек живёт рядом.
- **Менять сигнатуры контрактов** Stage 1 без явного approve (на них строятся компоненты).
- **CPU-реализации** AA / glow / скруглений / градиентов в `ModernBackend` — всё через шейдер; нельзя — оставь `// TODO`.
- **Временные решения и «костыли»** в постоянном коде. Demo/bootstrap/флаги для проверки — отдельно и удаляются перед merge.
- **Аллокации в render-хотпате** из своего кода (см. [PERFORMANCE.md](PERFORMANCE.md)).
- **Смешивать этапы.** Один Stage за раз. Не забегать вперёд.
- **Ускоряться за счёт качества.** Лучше остановиться и спросить, чем «готово, но криво».
- **Принимать архитектурные решения самостоятельно** — всегда approve пользователя.
- **Литералы цвета/размера** внутри компонентов (Stage 2+) — только токены.

## Стиль разработки (порядок неизменен)
```
Spec → (approve) → Plan → (approve) → Implementation → Code Review → Fix → Milestone Report → (approve) → Continue
```
Параллелить субагентами можно ТОЛЬКО когда спека утверждена и куски реально независимы (непересекающиеся файлы).
Параллель без утверждённой спеки запрещена.

## Как проходит каждая задача
1. Обсуждение/уточнение (вопросы по одному, мультивыбор где можно).
2. **Спека** (контракты/решения/критерий готовности).
3. **Approve** пользователя на спеку.
4. **План** реализации (файлы, порядок, точки проверки, тесты).
5. **Approve** на план.
6. **Реализация** (TDD где применимо; компиляция/тесты).
7. **Code Review** (по диффу; spec-compliance + качество; adversarial на финале этапа).
8. **Fix** найденного (Critical/Important — обязательно).
9. **Milestone Report** (формат ниже).
10. **Разрешение** пользователя двигаться дальше.

Крупные этапы Stage помечены чекпоинтами — на них стоп и отчёт, не авто-продолжение.

## Формат отчёта (как уже принято)
Архитектурный отчёт на майлстоуне содержит: **что сделано · принятые решения · компромиссы · остаточные риски ·
соответствие charter V2** (4 принципа: backend-only · нет low-level вне backend · контракты не менялись · gui/hud не
тронуты). По требованию добавляются разделы **Technical Risk Assessment** и **Performance Ledger** (живут в
`docs/UI-V2-RISKS.md` / `docs/UI-V2-PERF.md` — обновляй их, не дублируй в отчёте). Отчёты — компактные; главное —
качество кода, а не объём текста.

## Как работать с пользователем
- Пиши **коротко и по делу**. Пользователь ценит качество работы, а не длинные отчёты.
- **Всегда спрашивай approve** на спеку/план/архитектурные развилки. Молчание/«делай как лучше» ≠ approve — переспроси.
- Сначала фундамент → потом компоненты → потом стиль → потом функционал. Не нарушать порядок.
- Если контракт начинает ограничивать качество/производительность — **остановись и обсуди** до написания большого кода.
- Деструктив/необратимое (удаление, merge, push) — подтверждай и показывай, что именно делаешь.
- Веди живой статус в [CURRENT_TASK.md](CURRENT_TASK.md) и обновляй ledger-файлы по ходу.

## Окружение (практика)
Windows, fullscreen дев-клиент (guiScale 2). Сборка: `.\gradlew.bat compileJava` / `test` / `build` / `runClient`.
Рантайм-проверка рендера = headless-capture (гейченный bootstrap, который удаляется перед merge) + визуальный осмотр
скриншотов. MSDF-атласы генерит `genMsdfAtlas` (офлайн, скачивает pinned `msdf-atlas-gen`).
